# Multi-Agent 失控事件修复计划

> 文档状态：已实施
> 实施结果：终态交付去重、后台通知 Run、预算、无进展熔断、会话级停止和前端权威状态已经落地。完整复跑证据见 [`../records/multi-agent-incident-remediation.md`](../records/multi-agent-incident-remediation.md)。

## 1. 事件结论

目标会话 `session-e4661603-47a9-4271-8aed-04da5522ed61` 暴露的不是单一轮询错误，而是终态语义、后台通知、运行预算、停止语义和前端状态投影共同形成的失控链路。

已确认的关键事实：

- 原始主 Run 在一次阻塞等待超时后自然结束，但三个 Child Run 仍在后台执行。
- Child Run 随后因模型请求默认 120 秒超时而失败。失败是终态，不是“仍在运行”。
- Child 终态通知自动创建了新的 Main Run。该通知 Run 反复读取同一批终态、继续派生和重试，共执行 96 轮。
- 该通知 Run 内发生 85 次 `wait_agent`、14 次 `spawn_agent` 和 6 次 `followup_agent`；85 次等待均未超时，其中 84 次返回已有终态。这证明核心循环不是等待过久，而是重复消费没有进展的结果。
- 前端停止只按一个可能过期的 Run ID 发请求，且只有本地流或本地活动 Run 存在时才展示按钮。后台通知 Run 没有可靠进入这两个本地状态，因此用户可能看见持续输出却没有有效停止入口。
- 现有停止只终止 Main Run 或单个 Child Run，没有“停止整个会话编排链”的原子语义。Child 终止后产生的新通知还可能再次唤醒 Main Run。

## 2. 必须恢复的系统不变量

1. `failed`、`completed`、`interrupted` 和 `limited` 都是终态；终态不能被解释为后台仍在运行。
2. 同一个 Child Run 的终态对同一个调用方最多交付一次。重复读取必须明确返回“无新进展”，不能再次伪装成新完成结果。
3. 状态必须先持久化为终态，再发布完成通知。任何异步刷新都不能把终态覆盖回运行态。
4. 后台完成通知可以推动 Main 处理结果，但每批通知只能触发一个有界的处理链；通知处理不能无限派生新的通知处理链。
5. 保留开放编排能力，但每个 Main Run 和每个会话都必须具备可观测的操作预算、无进展检测和熔断状态。
6. 用户停止会话时，Main Run、所有 Child Run、待触发通知和延迟唤醒计时器必须作为一个控制域停止。停止完成前后都不能出现自动复活。
7. 前端停止按钮由后端权威快照驱动；只要 Main 或任一 Child 仍在运行，就必须可见并可操作。

## 3. 修复分层

### 3.1 持久化状态与通知交付

- 为 Agent 会话增加持久化的 `halted` 控制状态，以及明确的暂停、恢复和通知丢弃记录。
- 给终态交付增加调用方观察游标，区分“首次交付的终态”和“已经观察过、没有进展”。
- 恢复时先把遗留运行落为 `interrupted`，再根据会话是否已停止决定是否保留通知；停止状态下不得调度自动唤醒。
- 新的用户消息显式恢复会话编排能力；后台通知本身不能清除停止状态。

### 3.2 编排网关与熔断

- 对每个调用 Main Run 记录 `spawn`、`followup`、`wait`、`stop` 次数和 Agent Tree revision。
- 对重复终态观察、连续无 revision 变化和超出操作预算返回结构化的 `already_observed` / `circuit_open` 结果。
- 执行器收到熔断结果后终止当前通知处理 Run，结果标记为 `limited`，原因标记为 `orchestration_stalled`，而不是继续消耗剩余模型轮次。
- 通知处理 Run 使用独立的小预算；普通用户 Run 仍保留灵活编排空间。

### 3.3 Child 运行预算

- 将 Child 模型单次请求超时从隐式 120 秒改为显式、可配置且适合长任务的值。
- 将当前过宽的 200 模型轮次改为有依据的默认值，同时增加总令牌和总运行时上限。
- 分开记录请求超时、总运行时耗尽、总令牌耗尽和模型轮次耗尽，避免统一显示成含义不清的“未完成”。
- 保留 Agent Definition 覆盖能力，让确实需要更长时间的任务可以显式申请更高预算。

### 3.4 会话级紧急停止

- 新增按 Session ID 执行的 `stop_all` 后端命令。
- 命令顺序为：持久化停止闸门、取消延迟唤醒、停止 Main、停止全部 Child、等待 Child 落终态、处理停止过程中产生的通知、返回权威快照。
- 命令必须幂等。即使前端持有的 Run ID 已过期，也能停止当前会话中的实际运行。
- 运行时关闭、会话删除和用户紧急停止复用同一个底层停止协议。

### 3.5 前端状态与交互

- 停止入口由 `conversation.activeRun`、本地流状态和 Agent Tree 中的运行态共同决定。
- 停止操作改为按 Session ID 调用 `stop_all`，展示“正在停止”，并在返回后立即用后端快照校准会话和 Agent 状态。
- 后端返回未停止或请求失败时不能静默当作成功；界面保留可重试入口并展示具体原因。
- Child 终态文案区分失败、受限、中断和完成，不使用会误导为仍在执行的笼统表达。

## 4. 验证策略

高风险链路不直接以完整原任务作为第一项测试。按以下顺序逐级放大：

1. 纯状态机测试：终态只交付一次、停止闸门持久化、恢复时不自动复活。
2. 协调器测试：一批通知最多创建一个处理 Run；无进展达到阈值后熔断。
3. API 测试：过期 Run ID 不影响 `stop_all`；并发 Child 终止通知不能越过停止闸门。
4. 前端组件和状态测试：后台 Main、仅 Child 运行、停止中、停止失败四种状态都保留正确入口。
5. 受控集成测试：使用短任务和低并发，旁路采样进程、Main/Child 数量、Agent Tree revision 和令牌累计值；超过阈值立即 `stop_all`。
6. 宽屏浏览器验证：确认持续输出期间停止按钮始终可见，停止后 UI 与后端权威快照一致。
7. 原会话任务验收：在模型请求时限、总预算、无进展熔断和会话级停止均生效后重试。监控器独立于被测前端，达到任一阈值即终止整个会话编排链。

原任务验收的默认安全阈值：

- 同时运行 Child 不超过 4 个；会话 Agent 总数不超过 8 个。
- 通知处理 Run 不超过 20 个模型轮次。
- 连续 3 次编排操作没有 Agent Tree revision 进展时熔断。
- 单个 Child 模型请求允许覆盖约 3 分钟的正常工作，但仍受总运行时和总令牌上限约束。
- 监控器发现 Main Run 数量异常增长、停止后 revision 继续产生运行事件或通知链重复启动时，立即执行会话级停止并判定验收失败。

2. 修复后端状态、通知和会话级停止，提交对应测试。
3. 修复预算和无进展熔断，提交对应测试。
4. 修复前端权威状态投影与停止交互，提交前端测试。
5. 完成受控集成、浏览器和原任务验收，补充事件修复记录。
