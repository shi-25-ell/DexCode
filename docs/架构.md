# DexCode 当前架构

本文描述 `core-update` 重构后的生产链路。旧的 Planner → Orchestrator → Executor → Reviewer → Summarizer 方案已经废止，不再对应当前代码。

## 1. 范围

- 只支持 OpenAI 与 OpenAI-compatible Chat Completions streaming。
- 只维护 Windows 本地文件系统和进程执行语义。
- 使用单 Agent Run；没有 Orchestrator、任务分类、worker pool、多 Agent或强制模型 review。
- Web 是应用适配层，不拥有模型、Session 或工具执行状态。

## 2. 生产链路

```text
Web POST /api/agent/chat
  -> 为 HTTP 连接创建 runId 和 AbortController
  -> CodingAgent.runTask
  -> 构建 system/project/skill/transcript context
  -> SessionRepository.beginRun + commitContext
  -> Executor ReAct loop
       -> ModelClient.streamMessage
       -> OpenAI-compatible SSE parser
       -> canonical ModelEvent
       -> strict turn accumulator
       -> durable assistant commit
       -> tool schema / approval / guard / execution
       -> durable tool result
       -> 下一轮 model request 或终止
  -> SessionRepository.finishRun
  -> durable RunReport + task_status/result event
  -> bounded SSE writer
```

整个链路使用同一个 `runId`。HTTP 连接关闭会触发 abort，并向模型请求、retry wait、命令进程和外部 MCP 请求传播。

## 3. 模块职责

### `packages/llm-client`

- `openai.ts` 只处理 OpenAI-compatible wire protocol、鉴权、超时和错误归一化。
- `types.ts` 定义 provider-neutral 的 `ModelEvent`、`ModelResponse`、`ModelFailure`。
- `turn-accumulator.ts` 把 delta 严格归约成完整 turn，拒绝断流、非法 JSON tool arguments、缺少终态或响应不一致。
- Agent core 不读取 OpenAI 原始 chunk。

### `packages/agent-core`

- `index.ts` 是聊天 Run 的应用入口，负责 context projection、Session 提交和最终 `RunReport`。
- `executor.ts` 是单 Agent ReAct loop，管理 model turn/attempt budget、有限重试、abort 和工具调用顺序。
- `session-contracts.ts` 是 consumer-owned Session contract，隔离存储实现。
- 模型文本和 reasoning delta 是 progress；完整 assistant message、tool result 和 RunReport 才是 durable truth。

### `packages/session-store`

- 每个 Session 保存独立 JSON 文件。
- 写入使用同目录临时文件加 rename，避免半文件。
- 进程内按 Session 串行化 mutation；一个 Session 最多一个 active Run。
- ledger 记录 run start、消息、context manifest、tool start 和 terminal report。
- 重启后首次读取 active Run 会生成一次 `recovered_interruption` 终态。
- transcript 原文不会被 compaction 覆盖；checkpoint 和 source digest 单独保存。

### `packages/tool-gateway` 与 `packages/workspace-manager`

- 本地工具定义经 schema 校验后执行；未知参数、缺少必填字段和类型错误会在 effect 前拒绝。
- assistant message 和 tool-start ledger 必须先提交，之后才能产生工具 effect。
- 文件路径拒绝 absolute、drive、UNC、NUL 和 `..`，并检查已存在祖先中的 symlink/junction。
- 命令执行接收 `AbortSignal`，timeout 或 abort 时用 Windows `taskkill /T /F` 清理进程树。
- 高风险命令继续使用确认/白名单策略。
- 外部 MCP 工具必须经过用户确认；HTTP 与 stdio transport 支持超时和调用取消，stdio 不再通过 shell 启动。

### `apps/runtime`

- 负责 HTTP parsing、依赖组装、确认请求映射和 SSE projection。
- SSE writer 有容量上限，会合并连续 text/reasoning delta，并遵守 `res.write()` backpressure。
- 慢消费者优先丢弃 progress；若 semantic backlog 已满则中止 Run。
- `/api/agent/preview` 复用同一 Executor/Model stream，但不创建 durable Session Run。
- 模板 API 直接调用 template service，不挂在 CodingAgent facade 上。

### `apps/web`

- 合并 `chunk` 形成临时 assistant 内容。
- 展示 reasoning/tool progress、确认请求、终态和错误。
- 不处理旧的 `plan`/review/worker 事件。

## 4. Run 状态和终止语义

Durable Run 状态只有：

- `completed`：模型自然结束且结果完整。
- `aborted`：用户、HTTP 断开或上游 signal 取消。
- `failed`：provider、协议、执行基础设施或恢复失败。
- `limited`：model turn/attempt budget 用尽或输出被 provider 截断。

`RunReport` 记录 termination reason、开始/结束时间、model turn/attempt、usage、使用的工具、修改的文件和结构化错误。`finishRun` 按 `runId` 幂等，重复提交不会生成第二份报告。

## 5. Context projection

Session transcript 先校验 assistant tool call 与 tool result 的配对关系，再按估算 token budget 投影：

1. 未超预算时完整保留。
2. 超预算时保留以最近完整 user turn 开始的尾部。
3. 被省略的旧消息生成确定性 checkpoint。
4. 保存 source digest、策略版本、消息数量和最终 request digest。

当前算法是便于审计和恢复的基础实现，不是语义检索或模型摘要。

## 6. 事件协议

主要 progress 事件：

- `chunk`
- `reasoning_chunk`
- `tool_status`
- 执行中的 `task_status`

主要 semantic 事件：

- `tool`
- `confirm_request` / `command_confirm_request` / `confirm_resolved`
- terminal `task_status`
- `result`（包含 TaskSummary、LoopResult 与 RunReport）
- `error`

每条 SSE 以 `data: <json>\n\n` 发送，流末尾保留兼容标记 `data: [DONE]`。

## 7. 仍然明确保留的边界

- Session repository 当前仍是 JSON 文件，不是 SQLite；它保证单进程内的原子写和互斥，不提供多进程 writer fencing。
- Tool pipeline 已统一关键校验和提交顺序，但 Skill 控制工具仍由 Agent core 内部处理；不可信插件 sandbox 不在本轮范围。
- `/api/agent/preview` 是兼容接口，没有 Session durability。
- Context token 数是字符估算，基础 checkpoint 是确定性摘要。

这些边界不影响当前 Windows 单服务部署，但在引入多进程 daemon、插件生态或更大上下文前需要继续演进。
